P132 [align=JUSTIFY (3)]: PROBLEM / REQUIREMENT IDENTIFICATION AND ANALYSIS
P133 [align=JUSTIFY (3)]: Background and Context
P134 [align=JUSTIFY (3)]: In modern law enforcement and judicial proceedings, digital evidence such as CCTV video recordings, wiretaps, crime scene photographs and forensic disk images serves as critical proof in court. However, managing digital evidence introduces serious challenges regarding file authenticity, unauthorized access and evidentiary admissibility.
P135 [align=JUSTIFY (3)]: For digital evidence to be accepted, it must be shown that the evidence has not been altered since collection and that every person who handled it is accounted for. Standards such as ISO/IEC 27037 and NIST SP 800-86 describe the principles for identifying, collecting, acquiring and preserving digital evidence, including the need for an unbroken chain of custody.
P137 [align=JUSTIFY (3)]: Many organizations still store such evidence in ordinary shared folders or file servers. These provide no cryptographic proof of integrity, no reliable record of access and no protection if the storage itself is compromised. A dedicated secure system that combines cryptography, access control and auditing was therefore proposed.
P138 [align=JUSTIFY (3)]: Problem Statement
P139 [align=None]: Traditional file management systems suffer from the following major security weaknesses:
P140 [align=LEFT (0)]: Risk of Data Tampering: Files stored without cryptographic hashes can be modified or corrupted without detection, invalidating evidence in court.
P141 [align=LEFT (0)]: Broken Chain of Custody: Standard server directories do not log who accessed, viewed, downloaded or shared evidence, which violates ISO 27037 expectations.
P142 [align=LEFT (0)]: Unencrypted Plaintext Storage: Files saved in plain text on server disks expose sensitive legal artifacts to data breaches and insider threats.
P143 [align=LEFT (0)]: Slow Manual Investigation: Investigators spend considerable time searching unstructured folders to locate relevant evidence.
P144 [align=None]: Therefore, the problem was defined as:
P145 [align=JUSTIFY (3)]: “To design and develop a secure, web-based Digital Evidence Management System that guarantees evidence integrity using cryptographic checksums, protects evidence at rest using envelope encryption, records an immutable chain of custody, enforces role-based access, and assists investigators through an AI-based search assistant.”
P146 [align=JUSTIFY (3)]: Existing Process / Existing System
P147 [align=JUSTIFY (3)]: Before the proposed system, digital evidence was typically handled using conventional file-server directories, email attachments and manual registers. The existing process involved several individual activities:
P148 [align=LEFT (0)]: Manual Storage and Naming
P149 [align=None]: Evidence files were saved in folders organized by naming convention. Any user with folder access could modify, rename or replace a file without leaving a trace.
P150 [align=LEFT (0)]: No Integrity Verification
P151 [align=None]: No checksum was computed when evidence was collected, so it was not possible to demonstrate later that a file was identical to the original.
P152 [align=LEFT (0)]: Manual Custody Records
P153 [align=None]: Handover of evidence was recorded on paper or in spreadsheets, which are easy to alter and are not linked to actual file access.
P154 [align=LEFT (0)]: Plaintext Storage
P155 [align=None]: Files were kept unencrypted on disk, so anyone with access to the storage, a backup or the server could read them.
P156 [align=LEFT (0)]: Manual Search
P157 [align=None]: Locating evidence related to a case required browsing folders and opening files individually.
P158 [align=LEFT (0)]: Limitations of the Existing Process
P159 [align=LEFT (0)]: No tamper detection for stored files.
P160 [align=LEFT (0)]: No automatic record of who accessed or downloaded evidence.
P161 [align=LEFT (0)]: No encryption of evidence at rest.
P163 [align=LEFT (0)]: No role-based restriction of access.
P164 [align=LEFT (0)]: Slow and error-prone search for evidence.
P165 [align=LEFT (0)]: Difficult to demonstrate compliance with ISO 27037.
P166 [align=None]: These limitations provided the motivation for developing a secure evidence management system that brings integrity, confidentiality, accountability and search together in one platform.

P173 [align=JUSTIFY (3)]: Problem Analysis
P174 [align=JUSTIFY (3)]: The problem was analyzed by examining the activities involved in handling digital evidence from ingestion to retrieval. The analysis showed that evidence management involves several independent concerns: proving integrity, protecting confidentiality, controlling access, recording accountability and enabling efficient search.
P175 [align=JUSTIFY (3)]: A major technical challenge was designing the encryption approach. Encrypting every file directly with a single master key would make key rotation difficult and increase the impact of a key leak. Envelope encryption, in which each file uses its own Data Encryption Key (DEK) that is itself protected by a Master Key, was selected to address this.
P176 [align=JUSTIFY (3)]: Another challenge was ensuring that the audit trail could not be bypassed. The audit logger was therefore implemented so that it records the user ID, IP address, device user-agent, action and timestamp automatically for every relevant request, rather than relying on manual entries.
P177 [align=JUSTIFY (3)]: Authentication also required careful design. Passwords had to be hashed, tokens had to expire and rotate, brute-force attempts had to be limited and account recovery had to be verified through a second factor. Finally, the AI assistant had to give quick, reliable results from the evidence database even when an external LLM was unavailable, which led to the design of a live MongoDB regex search with optional Gemini integration.

P181 [align=JUSTIFY (3)]: Proposed Solution
P182 [align=JUSTIFY (3)]: CivicEvidence is a secure web-based Digital Evidence Management System that combines applied cryptography, role-based access control and AI-assisted search. The system consists of a React frontend, an Express.js backend, a MongoDB database and a cryptography and audit layer. The proposed solution provides the following features:
P183 [align=LEFT (0)]: SHA-256 Checksums: A cryptographic hash is computed on ingestion so that bit-level tampering can be detected instantly.
P184 [align=LEFT (0)]: AES-256 Envelope Encryption: Files are encrypted at rest with dedicated Data Encryption Keys protected by a Master Key.
P185 [align=LEFT (0)]: ISO 27037 Audit Logger: The user ID, IP address, device user-agent and exact timestamp are recorded for every action.
P186 [align=LEFT (0)]: Role-Based Access Control: Four clearance levels (Admin, Officer, Investigator, User) restrict access to routes and operations.
P187 [align=LEFT (0)]: Two-Factor Authentication: OTP codes sent by email verify identity during verification and password reset.
P188 [align=LEFT (0)]: Smart AI Assistant: A floating chat widget performs live MongoDB regex evidence lookup and provides legal compliance guidance.

Queries are first matched against the evidence database using a live MongoDB regex search, returning evidence titles, original filenames and SHA-256 hashes. For general or legal compliance questions, the Google Gemini API can be used as an optional LLM backend.

P264 [align=JUSTIFY (3)]: The Express server was configured with Helmet for secure HTTP headers, CORS for controlled cross-origin access and express-rate-limit to limit repeated requests. P265 [align=JUSTIFY (3)]: Authentication and 2FA OTP
P266 [align=JUSTIFY (3)]: The authentication controller implements registration, login, password complexity validation and OTP verification. Passwords are hashed with bcryptjs. Password reset uses a six-digit OTP sent by email; successful verification also marks the account email as verified.
P267 [align=JUSTIFY (3)]: Email Service
P268 [align=JUSTIFY (3)]: A central Nodemailer transporter using Gmail SMTP with an app password was configured to send OTP and password reset emails. This service is used by the authentication controller whenever an OTP must be dispatched.
P269 [align=JUSTIFY (3)]: Cryptographic Engine
P270 [align=JUSTIFY (3)]: The evidence controller uses the native crypto module. On upload, it computes the SHA-256 hash of the file, generates a DEK and IV, encrypts the content with AES-256-GCM, wraps the DEK with the Master Key and stores the encrypted file and its metadata. On download, the process is reversed and the hash is recomputed and compared with the stored value to confirm integrity.
P272 [align=JUSTIFY (3)]: Audit Logger
P273 [align=JUSTIFY (3)]: The audit logger utility extracts the user ID, IP address, user-agent, action and target from the request context and stores an audit record in MongoDB for each relevant operation. It is called from the controllers so that the Chain of Custody is built automatically.
P274 [align=JUSTIFY (3)]: RBAC Middleware
P275 [align=JUSTIFY (3)]: The role clearance guard verifies the JWT and checks the user’s role (Admin, Officer, Investigator or User) against the route policy before the controller is executed.
P276 [align=JUSTIFY (3)]: AI Assistant Engine
P277 [align=JUSTIFY (3)]: The AI controller receives the user’s prompt, performs a live MongoDB regex search against evidence records and returns matching titles, original filenames and SHA-256 hashes. For other questions it can call the Google Gemini API. The response is returned as Markdown with live statistics.
P278 [align=JUSTIFY (3)]: Frontend Dashboard and AI Chat Widget
